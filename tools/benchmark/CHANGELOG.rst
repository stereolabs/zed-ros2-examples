LATEST CHANGES
==============

v5.4.1
----------
- **The benchmark can now measure Intra Process Communication, including true zero-copy.** Previously it could not, and worse, it looked as though it could: composing it in the publisher's container was documented as a way to measure IPC, and `zed_check_ros2_config.sh` ran every topic twice to show the "IPC gain". Both runs actually measured the same inter-process path and returned identical figures. The cause is structural: subscribing to a topic whose type is only known at runtime requires an `rclcpp::GenericSubscription`, and rclcpp registers a subscription with the `IntraProcessManager` only from the templated `rclcpp::Subscription<T>` — on every distribution from Humble to Rolling. There is no serialized intra-process path at all. What changed:

  - New `subscription_mode` parameter: `generic` (the previous behaviour: any message type, exact wire bytes, never intra-process), `typed` (a compile-time typed subscription, the only kind that can take the intra-process path), or `auto` (the default: `typed` when intra-process comms are enabled on the node and the type is supported, `generic` otherwise). `auto` leaves ordinary separate-process runs exactly as they were, so their wire-accurate bandwidth figures are unchanged.
  - Typed subscriptions cover **every transport** of `image_transport` and `point_cloud_transport`, so a compressed, theora, ffmpeg, draco, zlib or zstd sub-topic can be benchmarked over the intra-process path just like the raw one: `sensor_msgs/msg/Image`, `sensor_msgs/msg/CompressedImage` (which serves the compressed, compressedDepth and zstd image transports), `sensor_msgs/msg/PointCloud2`, `sensor_msgs/msg/CameraInfo`, `sensor_msgs/msg/Imu`, `theora_image_transport/msg/Packet`, `ffmpeg_image_transport_msgs/msg/FFMPEGPacket` and `point_cloud_interfaces/msg/CompressedPointCloud2`. For a compressed cloud the *compressed* payload is reported, not the uncompressed geometry, which would overstate the transported volume by the compression ratio. The transport plugins are separate installable packages, so `theora_image_transport`, `ffmpeg_image_transport_msgs` and `point_cloud_interfaces` are optional build dependencies: each type is compiled in only when present, the build logs which ones it enabled, and anything else falls back to `generic` with a warning instead of silently measuring something different.
  - **True zero-copy** for image topics, by subscribing through the same `TypeAdapter<StampedSlMat, sensor_msgs::msg::Image>` the ZED node publishes with: the publisher's `sl::Mat` is received by pointer, with no serialization, no conversion and no copy. This tier needs `zed_components` and the ZED SDK, and is an **optional** build dependency — without it the benchmark still builds and still measures the plain typed intra-process path. The build logs which of the two it configured.
  - Added **end-to-end latency** (publisher `header.stamp` to arrival) and **process CPU** to the report and to the `BenchmarkStatsStamped` message (new `topic_latency` / `topic_avg_latency` fields). These, not bandwidth, are what reveal the IPC gain: on the intra-process path nothing is transported, so its bandwidth figure is notional and its frequency is simply whatever the publisher produces. Measured on a synthetic 1280x720 RGBA publisher at 20 Hz, composed zero-copy vs separate process: latency 0.02 ms vs 3.32 ms, CPU 0.34% vs 2.04% of one core, with frequency and message size identical in both.
  - Reports now always state the subscription path, the delivery path and how the message sizes must be read (serialized wire bytes vs message content bytes, which are not comparable). The delivery path distinguishes `CONFIRMED` intra-process zero-copy — provable only on the type-adapted path, because the custom C++ type received has no wire representation — from merely `intra-process capable`, since a typed subscription with intra-process comms enabled still takes the middleware for publishers in another process, and that cannot be checked from inside a callback.
  - `zed_check_ros2_config.sh` again runs each topic twice, but now the comparison is meaningful: `interprocess` vs `ipc`, both with a typed subscription so the accounting is identical, and with the ZED node keeping `enable_ipc:=true` in both so only the subscriber's location changes. The summary reports latency and CPU instead of bandwidth. Report files are named `report_<mode>_<topic>.txt`.
  - The summary's CPU column is the total across **every** process involved (ZED node + benchmark for `interprocess`, the ZED node alone for `ipc`, where the benchmark runs inside it), plus a `CPU_IDLE` no-subscriber baseline so the transport cost reads as `CPU_TOT - CPU_IDLE`. The per-process figure in an individual report is *not* comparable between the two modes: composed, that process is the ZED node, so it also covers capture, depth and publishing. Measured on a ZED 2i the per-process figures are 6.2% separate vs 89.4% composed, which naively suggests IPC is far worse, while the totals are 93.6% vs 89.4% - the other way around.
  - **The subscriber QoS is now configurable**, through four parameters that are effective on *every* subscription path: `qos.reliability` (`best_effort`, `reliable`), `qos.durability` (`volatile`, `transient_local`), `qos.history` (`keep_last`, `keep_all`) and `qos.depth`. The defaults reproduce the previous behaviour (Best Effort, Volatile, `KEEP_LAST`, depth 1), so nothing changes unless asked. They work where ROS 2's own `qos_overrides.*` cannot, by setting the QoS *argument* of the subscription rather than relying on parameter plumbing that a generic subscription never reads. An unrecognised value falls back to the default **and warns**, a `qos.depth` below 1 is clamped to 1 with a warning, and the report shows the QoS the middleware actually granted, read back from the subscription instead of echoing the request. A Reliable subscriber cannot match a Best Effort publisher - which is how ZED image and cloud topics are published - so selecting `reliable` also logs that caveat up front, and the report then pairs the QoS with `No message received` so the cause is visible.
  - Fixed a wrong instruction in the documentation: the QoS section told the user to change the subscriber reliability with `-p qos_overrides.<topic>.subscription.reliability:=reliable`, which the default `generic` path silently discards. `rclcpp::create_generic_subscription()` forwards the subscription options but never calls `declare_qos_parameters()`, so no `qos_overrides.*` parameter is declared and the request never reaches the endpoint - on the `humble`, `jazzy`, `lyrical` and `rolling` branches alike. Confirmed three ways: `ros2 topic info -v` still reports `BEST_EFFORT`, `ros2 param get` answers "Parameter not set", and the parameter is absent from `ros2 param list`. The QoS of that path is fixed at Best Effort, `KEEP_LAST`, depth 1. What changed:

    - The documentation now carries a warning instead of the broken recipe, and the report states `Subscriber QoS: ... - FIXED, qos_overrides ignored` on the generic path.
    - The node **warns** at start-up when it is given a `qos_overrides.<topic>.subscription.*` it cannot honour, so the request is refused visibly rather than dropped in silence.
    - `subscription_mode:=typed` **does** honour QoS overrides, because `rclcpp::create_subscription()` calls `declare_qos_parameters()`. Verified end to end: the parameter reads back as `reliable` and the endpoint reports `RELIABLE`. This is now the documented way to change the QoS, and a unit test asserts it so it cannot regress silently.
    - Corrected a second inaccuracy while documenting the alternative: `ros2 topic hz` and `ros2 topic bw` expose no QoS options at all and hard-code `qos_profile_sensor_data`, so they share the same Best Effort limitation. Only `ros2 topic echo` accepts `--qos-*`.

  - Hardened `zed_check_ros2_config.sh` after a full validation run on a Jetson AGX Orin with four GMSL2 cameras, where three separate issues each cost part of the matrix silently:

    - The ros2 CLI daemon caches the ROS graph, and a stale cache made `ros2 component load` fail with "Unable to find container node" while the container's service was working, and `ros2 topic list` return an incomplete graph so every test was skipped as "topic not available". The daemon cache is now dropped once at start-up, and the component load retries once after dropping it.
    - The no-subscriber CPU baseline was sampled ~3 s after the topics appeared, while the neural depth engine was still initialising. That produced a `CPU_IDLE` *above* `CPU_TOT`, i.e. a negative transport cost. There is now a `WARMUP` wait (default 25 s, configurable) before the baseline, the baseline window grew to 6 s, and the summary explains that a `CPU_IDLE` above `CPU_TOT` means the warm-up was too short.
    - The script passed only `camera_model` and no serial number, so on a multi-camera rig the wrapper had to pick a camera itself and often opened none. A `CAMERA_SN` variable now passes `serial_number:=` through, and the header explains that it is strongly recommended with more than one camera attached.

  - Corrected two claims in the documentation that the Jetson run disproved. The wrapper publishes with `rclcpp::QoS(1)`, i.e. the default profile, which is **Reliable**/Volatile - not Best Effort as previously stated - so `qos.reliability:=reliable` works on ZED topics (verified, 40/40 messages) while `qos.durability:=transient_local` is the request that is genuinely incompatible (verified, 0 messages, with the node reporting `DURABILITY_QOS_POLICY`). The start-up log now warns about `transient_local` as well, and no longer asserts that ZED topics are Best Effort. Separately, `camera_info` does *not* time the transport alone: the wrapper stamps it from the frame timestamp like every other topic, and it measured 47.5 ms on the Jetson against the 0.09 ms once observed on a desktop, so `use_pub_timestamps` is now presented as the only reliable way to get a transport-only figure.
  - A report for a topic that was never seen now says `Subscription: none - the topic was never seen` instead of printing the default `generic (runtime-typed)` path, which asserted a subscription that had never been created.
  - `find_zed_pid` in `zed_check_ros2_config.sh` now excludes the benchmark process. The benchmark links the ZED SDK itself for the type-adapted path, so identifying the camera node by a mapped `libsl_zed` alone could match the benchmark and count its CPU twice.
  - Verified on a **Jetson AGX Orin** (JetPack 6 / L4T R36.5) with GMSL2 cameras, where the benefit is much larger than on a desktop. Single ZED X Mini at HD1200 (8.79 MB, 30 Hz, ~2.1 Gbps): latency 48.3 ms composed vs 54.2 ms separate, transport CPU 14.8% vs 38.3% of one core. Four cameras (2x ZED X Mini + 2x ZED X, ~8 Gbps aggregate) in one container, all four confirming zero-copy: 116.3 Hz aggregate at 161% CPU composed, against 95.9 Hz at 287% CPU as separate processes - the middleware cannot sustain the rate and every camera drops frames.
  - Documented that the ZED node stamps images and clouds with the frame **acquisition** time (`sl::TIME_REFERENCE::IMAGE`), so the reported latency covers the whole camera pipeline and only the difference between the two modes reflects the transport. On a ZED 2i the rectified RGB image reports ~18-20 ms in both modes, of which ~2 ms is transport, whereas `camera_info` - built at publish time - reports 0.09 ms. The wrapper's `use_pub_timestamps` parameter switches every topic to publish-time stamping for a transport-only measurement.
  - `zed_test_ipc.launch.py` gained a `subscription_mode` argument (default `typed`), applied to both the composed and the separate-process branch so `use_ipc:=True`/`False` are directly comparable.
  - `zed_test_ipc.launch.py` also exposes the subscriber QoS - `qos_reliability`, `qos_durability`, `qos_history`, `qos_depth` - plus `avg_win_size`, all applied to both branches. The two branches now share a single parameter dictionary instead of each carrying its own copy: they had already drifted, the separate-process branch using `avg_win_size` 5000 against the composed branch's default of 500. Since the report min/max are tracked on the windowed average, that asymmetry alone made a `use_ipc:=True` run not comparable with a `use_ipc:=False` one. The window is now symmetric and configurable, defaulting to the node's own 500.

- Added support for ROS 2 Lyrical Luth. The benchmark packages previously built only on Humble, Iron and Jazzy: on any other distribution they were silently configured as empty, so the workspace build succeeded but the message, the component library and the `zed_topic_benchmark` executable were never produced. The distribution check is now an exclusion list (only Foxy and older lack the "generic subscription" API this tool requires), so Lyrical, Rolling and future releases build without further changes. On an unsupported distribution the packages now emit an explicit warning and are still registered in the ament index.
- Added the `zed_check_ros2_config.sh` script to validate a ROS 2 setup. It benchmarks the ZED RGB image, depth and point cloud topics, in both standard and IPC (composition) mode, and prints a report for each test so the user can verify that their ROS 2 / DDS / system configuration delivers the camera data at the expected rate and bandwidth. Run it with `ros2 run zed_topic_benchmark zed_check_ros2_config.sh <camera_model>`.
- Added the possibility to run the benchmark for a limited time or number of samples and to save a report:

  - New parameter `test_duration_sec`: the test stops after the given number of seconds (`0` = infinite, default).
  - New parameter `test_sample_count`: the test stops after the given number of received messages (`0` = infinite, default).
  - New parameter `log_file_path`: when set, the final report is also written to this file.
  - When the test completes (a limit is reached) or is interrupted with `Ctrl+C`, a summary report is printed to the console listing the topic name/type, the stop reason, the test duration, the number of received messages, the total received data, and the mean/min/max of frequency, message size and bandwidth over the whole test.

- Fixed the report *min/max* frequency and bandwidth, which showed meaningless extremes (e.g. a max frequency of hundreds of kHz) caused by a single short inter-arrival interval. They are now tracked on the windowed average rate, after the averaging window has filled.
- Improved the report and live message-size display to use adaptive units (B / KB / MB / GB) so small messages (e.g. IMU samples) are no longer rounded to `0.00 MB`.
- Reworked the live console line into a compact, fixed-width `instant/average` format that fits within 80 columns. Previously the long line wrapped on a default-size terminal, which broke the in-place (carriage-return) update and flooded the console with one line per message. An ANSI "erase to end of line" is also emitted to clear any leftover characters.
- Fixed the windowed *average frequency* and *average bandwidth* statistics, which were biased high. The averages are now computed on the message periods and sizes (`1/mean(Δt)` and `mean(size)/mean(Δt)`), matching the unbiased windowed rate used by `ros2 topic hz`. Reported averages were previously optimistic, increasingly so on jittery topics.
- Fixed wrong statistics when multiple benchmark components run in the same process via IPC composition (e.g. the multi-camera launch): a shared initialization flag caused every node but the first to emit one garbage sample. Each component now keeps its own state.
- Fixed *average bandwidth* on variable-size topics (compressed images, point clouds): it now uses the windowed mean message size instead of the latest message size.
- Changed the default subscriber QoS reliability to `Best Effort` so the tool connects to sensor-data topics (images, point clouds) out of the box. Override to `Reliable` at runtime with `-p qos_overrides./<topic>.subscription.reliability:=reliable` if needed.
- Fixed possible `inf`/`NaN` statistics caused by unmeasurable inter-arrival intervals and empty averaging windows.
- Switched interval timing to a monotonic clock (`steady_clock`) for correct measurements under host clock adjustments (NTP/PTP).
- Fixed the `zed_test_ipc.launch.py` launch file failing to start due to an accidental `sympy` import.
